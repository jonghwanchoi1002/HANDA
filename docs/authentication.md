# 회원가입과 관리자 승인

## 현재 구현 범위

| 역할 | 공개 페이지 | 비즈니스 위키 | 회원 승인 관리 | 콘텐츠 작성 |
| --- | --- | --- | --- | --- |
| 방문자 | 가능 | 불가 | 불가 | 불가 |
| 승인 대기·거절 회원 | 가능 | 불가 | 불가 | 불가 |
| 이메일 확인 및 승인 완료 회원 | 가능 | 가능 | 불가 | 불가 |
| 이메일 확인 및 승인 완료 관리자 | 가능 | 가능 | 가능 | 후속 구현 |

Better Auth 1.7.10으로 이메일·비밀번호, 이메일 확인, 비밀번호 재설정, 세션, Google OAuth를 처리합니다. 모든 신규 계정은 `member / pending`으로 생성됩니다. 가입 요청에서 관리자 권한이나 승인 상태를 지정할 수 없습니다.

`/login`에서 가입·로그인하고 `/account`에서 상태를 확인합니다. `/admin`은 개발 도구가 아니라 홈페이지 운영자가 사용하는 회원 승인 화면입니다. 최신 신청자를 최대 100명까지 표시하며, 승인·거절·이용 중지를 처리합니다. 다른 관리자 권한 변경은 이 화면에서 제공하지 않습니다.

위키는 레이아웃과 서버 데이터 조회에서 권한을 검사합니다. 공개 홈페이지에는 위키 제목·요약·본문을 표시하지 않습니다. 세션 쿠키의 역할 값을 믿지 않고 매 요청에서 DB의 현재 공개 권한을 확인합니다. 기존에 다운로드한 정보를 이용 중지 후 기기에서 회수할 수는 없지만, 이후 요청은 차단합니다.

## 1. 개발용 DB에 새 테이블 적용

현재 브랜치에서 의존성을 설치하고, `.env.local`의 DATABASE_URL이 **Neon development**를 가리키는지 먼저 확인하세요.

```bash
npm ci
npm run db:migrate
```

기존 001은 건너뛰고 `002_member_auth.sql`을 적용합니다. 기존 콘텐츠는 삭제하거나 다시 넣지 않습니다.
마이그레이션은 Better Auth의 설치된 버전에서 생성한 스키마와 HANDA 권한·감사 기록 제약을 포함합니다. 배포 시 자동 실행하지 않습니다. Better Auth 버전을 바꿀 때에는 스키마 변경도 검토하세요.

## 2. 인증 기본 설정

`.env.local`에 추가합니다. 예시 파일의 빈 값은 실제 값으로 입력해야 하며 Git과 채팅에 공유하지 마세요.

```dotenv
BETTER_AUTH_URL=http://localhost:3000
BETTER_AUTH_SECRET=직접_생성한_비밀_문자열
```

PC 터미널에서 안전한 무작위 비밀 문자열을 생성할 수 있습니다.

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

출력값을 `.env.local`에만 저장하세요. 임의의 짧은 비밀번호를 대신 넣지 마세요. 운영과 개발은 서로 다른 secret을 사용합니다. 같은 development DB를 쓰는 PC와 Preview는 같은 개발용 secret을 사용하세요. 저장된 OAuth 토큰 암호화에도 사용하므로 설정 후 임의로 바꾸면 기존 로그인과 토큰에 영향을 줍니다.

인증 설정이 없으면 로그인이 비활성화되고 위키는 잠깁니다. 테스트용 관리자나 비밀번호를 자동으로 만들지 않습니다.

## 3. Google 로그인 설정

Google Cloud Console에서 OAuth 클라이언트를 **웹 애플리케이션**으로 만듭니다. 동의 화면을 설정하고 테스트 모드라면 실제로 시험할 Google 계정을 테스트 사용자로 추가하세요.

개발용 설정:

- Authorized JavaScript origin: `http://localhost:3000`
- Authorized redirect URI: `http://localhost:3000/api/auth/callback/google`

발급받은 값을 `.env.local`에 보관합니다.

```dotenv
GOOGLE_CLIENT_ID=발급받은_클라이언트_ID
GOOGLE_CLIENT_SECRET=발급받은_클라이언트_비밀값
```

Google로 가입한 사람도 관리자 승인을 받기 전에는 위키에 접근할 수 없습니다. 기존 이메일 계정과 자동 연결할 때에는 기존 이메일 확인과 Google의 확인된 이메일을 요구하는 라이브러리의 보호 규칙을 유지합니다.

Production의 콜백은 `https://handa-gules.vercel.app/api/auth/callback/google`입니다. Production의 BETTER_AUTH_URL은 `https://handa-gules.vercel.app`로 설정합니다.

Preview OAuth는 사용할 고정 브랜치 URL을 Vercel에서 확인해 BETTER_AUTH_URL과 Google 허용 콜백에 정확히 등록하세요. 모든 `*.vercel.app`을 신뢰하도록 범위를 넓히지 않습니다. 환경별 URL이 다르면 이메일 링크와 OAuth 콜백 주소도 달라집니다.

## 4. 이메일 가입과 비밀번호 재설정 메일

현재 메일 발송은 Resend API를 사용합니다. Resend에서 발송용 API 키와 검증된 발신 주소를 준비하고 설정합니다.

```dotenv
RESEND_API_KEY=발급받은_메일발송_API키
MAIL_FROM=HANDA <검증된_발신_주소>
```

메일 설정이 있어야 이메일 가입·로그인이 활성화됩니다. 이메일 확인 링크의 유효 시간은 1시간입니다. 비밀번호는 12~128자이며, 해시로 저장합니다. 비밀번호 재설정 후 기존 세션을 해제합니다. 로그인과 메일 요청 횟수 제한은 DB에 저장합니다.

**아직 도메인이 없는 경우:** Resend의 `onboarding@resend.dev` 테스트 발신자는 Resend 계정 소유자의 이메일로 제한된 테스트에 사용할 수 있습니다. 일반 회원에게 메일을 보내려면 본인이 소유한 발신 도메인의 DNS 검증 등 Resend 요구사항을 충족해야 합니다. 무료 `vercel.app` 주소의 DNS 소유권을 가졌다고 가정해서는 안 됩니다. Google 로그인부터 테스트한 뒤 이메일 실발송을 별도로 연결해도 됩니다.

발송 오류는 서버에 일반적인 오류 메시지로 남기고 비밀번호·토큰·수신자·메일 내용을 로그에 출력하지 않습니다. 실제 배송 성공은 공급자 발송 기록과 받은 편지함에서 별도 확인하세요.

## 5. 최초 관리자 지정

1. 홈페이지에서 운영자가 사용할 계정으로 가입합니다.
2. 이메일 링크 또는 Google 로그인으로 이메일 확인을 마칩니다.
3. 개발자가 같은 DB를 선택한 터미널에서 정확한 이메일을 지정합니다.

```bash
npm run admin:grant -- "운영자가_가입한_이메일"
```

기존의 이메일 확인 완료 계정만 관리자로 지정됩니다. 첫 가입자가 자동 관리자가 되지는 않습니다. 운영자는 이후 `/account`의 **회원 승인 관리** 링크로 `/admin`에 들어가 신청을 처리합니다. 관리자 지정과 승인·거절 변경은 `handa_membership_audit`에 기록합니다.

DB가 분리되어 있으므로 개발 관리자와 운영 관리자는 각각 지정해야 합니다. 운영 DB 변경은 개발 검증 후 별도 단계에서 수행하세요.

## 6. 확인 순서

설정 후 개발 서버를 재시작합니다.

```bash
npm run dev
```

- 시크릿 창으로 위키 목록·상세 주소를 직접 열어도 로그인 화면으로 이동하는지 확인합니다.
- 가입 → 이메일 확인 → 로그인 후 승인 대기 화면을 확인합니다.
- 관리자 계정으로 `/admin`에서 승인합니다.
- 같은 회원이 위키를 볼 수 있고 관리자 화면에는 접근할 수 없는지 확인합니다.
- 관리자가 이용 중지한 뒤 회원이 위키를 다시 요청하면 접근이 차단되는지 확인합니다.
- 로그아웃 뒤 위키 접근이 차단되는지 확인합니다.
- 이메일 확인·비밀번호 재설정 메일과 Google 실제 콜백을 각각 확인합니다.

Google Cloud·메일 공급자 실계정은 로컬 자동 테스트가 대신 검증하지 않습니다. 실제 설정이 완료되기 전에는 가입 기능이 모두 준비됐다고 판단하지 마세요.

## 운영 배포 순서

개발 DB에서 위 절차를 검증한 뒤 Production DB에 002를 적용하고 Vercel Production에 인증 URL·별도 secret·Google·메일 설정을 등록합니다. 코드 병합과 배포 후 운영 계정의 가입·관리자 지정을 확인합니다. Preview 환경에는 개발 DB와 개발용 인증 설정을 사용하고 운영 비밀값을 넣지 않습니다.

아직 콘텐츠 작성·수정·사진 업로드 기능은 없습니다. 이 기능의 서버 API도 관리자 권한을 별도로 검사하도록 후속 구현해야 합니다.

## 개발 검사

```bash
npm run lint
npm run test:auth
npm run test:db
npm run test:access
```

인증 테스트는 로컬 DB와 메일 수집 함수를 사용하며 외부에 이메일을 보내지 않습니다. Google 요청 생성과 잘못된 OAuth 상태값 거절은 검사하지만 실제 Google 토큰 교환은 포함하지 않습니다. 접근 테스트는 빌드 후 로컬 Next.js를 띄워 HTML/RSC의 위키 유출 방지와 권한 변경을 검사합니다. 로컬 테스트 포트 3900, 55439, 55443, 55445를 사용합니다.

## 로그인 화면에서 인증 테이블 누락 오류가 나는 경우

개발 서버를 종료하고 `npm run auth:check`를 실행하세요. 비밀 값 없이, 읽은 환경 파일 이름과 현재 연결에서 보이는 인증 테이블·마이그레이션 이름만 표시합니다. `MISSING`이면 `.env.local`의 주소가 Neon development인지 확인한 후 `npm run db:migrate`를 실행합니다. 모두 OK이면 개발 서버를 재시작하세요. 인증 라이브러리가 이전 초기화 오류를 기억하고 있을 수 있습니다.

로컬 DB 명령도 next dev와 같은 개발용 환경 파일 순서를 사용합니다. `.env.development.local` 또는 터미널에 설정한 환경 변수가 `.env.local`보다 우선할 수 있습니다. 운영용 명령을 별도 환경 파일로 실행할 때에는 `NODE_ENV=production`을 명시하고 대상 DB를 확인하세요. 오류 안내에 나온 `npx auth migrate`를 별도로 실행하지 말고 프로젝트의 `db:migrate`로 변경 이력을 유지하세요.
